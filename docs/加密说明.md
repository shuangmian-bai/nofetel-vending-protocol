# 加密与鉴权说明（Phase 2）

本文件回答一个问题：**这套协议到底有没有加密参数需要还原？**

## 结论

**没有。** 依据（逐条可复核）：

| 检查项 | 结果 | 证据 |
|---|---|---|
| 请求签名（sign / X-Sign / EDK） | 无 | `utils/api.js` 的 header 只拼 `app-id` / `user-id` / `version` / `page-path` / `qr-code` / `scene-code` |
| 时间戳 / nonce 参与签名 | 无 | 同上，无任何 ts/nonce 字段 |
| 请求体加密 | 无 | `content-type: application/json`，明文 body（`orderInfo` 结构可读） |
| 响应加密 | 无 | 返回明文 JSON，`code` 即业务状态 |
| 客户端硬编码密钥 | 无 | 全包检索 `appSecret|secretKey|apiKey|PRIVATE KEY|AES/CBC` 均无命中 |
| 指纹 / 风控头 | 无 | 客户端仅上报 `version`，未带机型/设备指纹 |

对比同目录已知案例（美团 RMS 的 TTE/EDK 加密头），本项目属于**完全裸接口**类。

## 鉴权强度评估（实测，非推断）

只带 `app-id` + `user-id`(openId) + `version`，未带令牌、未带 cookie 的情况下：

| 接口 | 结果 |
|---|---|
| `/front/dev/getModelConfig` | 200，返回完整机型配置 |
| `/front/dev/info` | 200，返回房间号、蓝牙 MAC、酒店 ID |
| `/front/item/info` | 200，返回货道商品与价格 |
| `/front/user/getUserInfo` | 200，返回该 openId 的用户档案 |

**结论**：`user-id` 即身份，服务端不做二次校验。openId 因此等价于账号口令，
必须按凭据管理（见项目 `CLAUDE.md` 第 1 条）。

**更强的实测结果（2026-11-18）**：把 `user-id` 留空（完全匿名）时，
`/front/dev/getModelConfig`、`/front/dev/info`、`/front/item/info` 依然返回 200 与完整数据
（含房间号、蓝牙 MAC、货道价格）。即**设备侧只读数据无需任何身份**，身份只在
用户数据与写操作（下单/支付/开柜）上被校验。

因此 CLI 在无 `VAULT_NOFETEL_OPENID` 时会打印警告：
只读命令仍可跑（这是服务端行为，不是我们的放行），写命令直接以退出码 2 拒绝。

## 唯一"加密"物：payCode

`getPayStatus` 返回的 `payCode` 是一串十六进制，蓝牙直接写进特征值。

- 它**不是**本地可计算的签名：客户端从不生成它，只透传；
- 它由服务端在确认支付后生成，与订单绑定；
- 因此本项目把它当作**不透明令牌**处理，不尝试逆向其生成算法。

推断（未验证）：payCode 由服务端按 `订单 + 货道 + 密钥` 生成，设备侧固件校验。
验证计划：见 `docs/逆向计划.md` 的「不做」一节——该逆向需要固件，超出本项目范围。

## 需要实证的遗留点

| 结论 | 状态 | 验证方式 |
|---|---|---|
| `status ∈ {1,12}` 均代表已支付 | 代码依据充分，**未跑真实支付** | 完成一次真实支付后观察返回 |
| payCode 与货道一一绑定 | 推断 | 观察多货道订单的 payCode 长度/内容差异 |
| 订单金额是否服务端二次核价 | 推断（客户端也有 getDevItemInfo 刷新价） | 真实下单后核对订单金额 |
